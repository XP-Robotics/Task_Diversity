full_diversity_pipeline  ·  control flow reference

Two QA pipelines,
one spine

Both walk the same path — ingest, normalize, check, report, exit. They part company on the question they ask: is the delivery balanced? against is each episode well‑formed?

run.py→ ingest→ normalize→ checks→ report · json + html + console→ exit 0 / 1 / 2

Each qa/ package fills the same slots: config and ruleset hold thresholds as data, normalize flattens metadata and resolves field aliases onto canonical keys, profiles merges per-delivery aliases into the live registry, and s3client is a stdlib SigV4 implementation with no boto3 dependency. Exit codes match: 0 clear, 1 data failure, 2 usage or ingest error.

Severity folds into verdict

Reject

ERROR

The only blocking severity. One ERROR anywhere in a session rejects the package; the vendor must redeliver.

Review

BLOCKED

Held for a human, but explicitly not the vendor's fault. Separating this from REJECT is the point of the model.

Accept

WARNINFOCEILINGFORMAT_GAPPASS

Everything else still ships. CEILING marks a device limit; FORMAT_GAP marks a field the capture app cannot express.

Why CEILING and FORMAT_GAP exist. They let the report say “the capture app cannot express this field” without recording it as a data defect, so the vendor is not penalised for a limitation of the tooling.
Collapsing. _collapse() keys on (id, severity, code, message), so a six-chunk session missing device_type reports once with the chunk list attached — while two chunks with genuinely different duration conflicts stay two records.
